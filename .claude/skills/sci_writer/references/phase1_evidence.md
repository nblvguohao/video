# Phase 1 详解：证据收集

## 0. 环境探测（在设计任何维度之前先做）

用 Bash 批量探测网络可达性，例如：

```bash
for u in "https://target-site-1.com" "https://target-site-2.com" ...; do
  code=$(curl -sS -o /dev/null -w "%{http_code}" --max-time 15 -L "$u" 2>&1)
  echo "$code  $u"
done
```

覆盖：案例主体官网、行业协会/政府数据库、金融/公告披露站点、目标期刊候选的出版社站点、通用学术 API（Crossref、OpenAlex、Semantic Scholar 等）。记录哪些可达、哪些 403/EGRESS_BLOCKED。常见例外：`github.com` 与 `raw.githubusercontent.com` 往往在白名单里,即使几乎所有其他站点被拦截——这意味着"搜索 GitHub 上是否有人已经把目标行业的公开记录汇编成结构化数据集"值得作为标准动作。

同时用 `ToolSearch` 探测已连接的学术 MCP 服务器（Consensus、Elicit、Scholar Gateway、Undermind、PubMed、Amass、bioRxiv 等），试调用一次确认：是否需要先 `get_orientation()`；是否有会话/月度配额，配额还剩多少；返回格式是否会超长需要分块读取。**不要假设某个工具一定可用或一定不可用**——每个环境配置不同。

把探测结果写成一段"工具与环境约束"文字（ENV_NOTE），后续每一个并行代理的 prompt 都要粘贴这段说明。这能避免十几个代理各自用同一个被拦截的域名浪费十几次超时重试。

## 1. 设计证据维度

典型的 8–12 个维度（按案例调整）：

1. **案例主体基本面**：逐年财务/规模/组织面板（收入、利润、细分业务、人员、资产负债关键项）
2. **核心产出/产品组合**：如果案例主体有可枚举的"产品级"记录（专利、审批文号、发布版本、门店、项目……），这往往是后续定量分析的核心数据来源，值得单列一个维度深挖
3. **研发/项目/合作网络**：研发平台、承担的政府项目、学术合作、获奖
4. **商业模式与产业链位置**：明确要求"同时检索该模式的争议报道、监管问询、负面财务后果"——不要只搜正面新闻
5. **行业与政策背景**：政策事件时间线、行业统计数据、竞争对手对照数据
6. **学术文献扫描 A（方法学范本）**：找"和你想做的分析方法类似"的已发表论文
7. **学术文献扫描 B（理论框架）**：找"你的研究问题所在学科的理论脉络"
8. **案例主体在文献中的直接记载**：哪怕数量很少也要如实报告，这个数字本身是"这块是不是空白"的证据
9. **数据可行性探针**（见下节，通常应当单独作为一个维度或提前进行）
10. **目标期刊预扫描的起步**（可以留到 Phase 3 集中做，但先摸个底有利于 Phase 2 提案人判断可行性）

## 2. 数据可行性探针——最容易被跳过但最重要的一步

不要等到 Phase 2 提案人说"这个变量应该能查到"才发现查不到。提前做：

- 从候选数据源里**随机抽取一批具体记录**（如 10–15 条，跨越不同年份/类别），对每条逐一检索关键字段，记录成功率、需要的检索次数、错配率（例如"检索到的是名字相近的另一个实体"）。
- 如果依赖某个第三方汇编数据集，**独立验证它的准确率**：抽样与你能找到的原始来源（哪怕只是摘要）比对。
- 明确报告：哪些字段覆盖率高（可放心用作核心变量）、哪些覆盖率低或缺失非随机（必须在分析中显式处理或换指标）、哪些渠道完全查不到（如实承认，不要靠"应该可以"蒙混）。
- 给出 2–3 个"可行数据集方案"，每个方案标明样本量、变量清单、获取工作量估算、主要风险，供 Phase 2 提案人选择。

## 3. 处理结构化字段的系统性缺失

真实的公开数据几乎必然有缺口。常见情况：某个身份字段（申请人、责任方、所有者）在某几年的记录里整体缺失（不是随机缺失，往往是数据源格式变化导致）。

处理方法：
1. 如实记录缺失的范围（哪些年份/哪些子集），不要平均掉。
2. 找**替代识别信号**——命名规律、编号前缀、关联实体名称、专有代号等。
3. **在有标签的子集上验证替代规则的精确率与召回率**，只有精确率足够高（比如 ≥0.95）才能用于扩展识别范围；召回率不足没关系，只要保证不引入假阳性，扩展后的样本仍然是"保守估计"。
4. 把这个识别规则、验证过程写成独立的证据文件，Phase 2/4 都要引用它。

## 4. Workflow 并行执行模式

```
phase('Sweep')
const sweep = await parallel(DIMS.map(d => () =>
  agent(`${ENV_NOTE}\n\n任务：${d.prompt}\n\n把结果写入 evidence/${d.file}。返回 key_facts 与 gaps。`,
    { label: `sweep:${d.key}`, phase: 'Sweep', schema: SWEEP_SCHEMA })
))
```

每个维度 15–30 次检索直到边际收益趋零；用 schema 强制返回结构化的 `key_facts`（10–25 条，含数字+来源 URL）与 `gaps`。

**并发限制提醒**：workflow 的并发数通常被硬件核数限制在个位数，一次性起太多并行 `agent()` 会排队而非同时跑。如果证据维度多，拆成 2–3 批 `Workflow` 调用（每批 3–4 个维度）通常比一次起十个更稳，也更方便中途检查进度、必要时重跑某一批。

**后台任务的脆弱性**：`Workflow` 的后台任务在会话被中断（模型切换、长时间挂起）时可能被杀掉且不会自动恢复。如果观察到这种情况（journal 长时间没有新事件，但任务显示仍在运行），改用前台的 `Agent` 工具逐个补跑缺失维度，保持会话活跃直到完成。

## 5. 完整性批评与补漏

跑完一轮后，派一个"完整性批评者"通读全部证据文件，输出：缺失的关键事实/数据、证据薄弱或矛盾之处、文献覆盖空白、未查的来源类型。给出最多 8–12 个 gap，每个附具体检索计划。再派并行代理补漏，每个 gap 独立处理，**追加**而非覆盖已有文件。

## 6. 事实核查

对决策关键的数字（会直接影响 Phase 2 选题的那些），派独立视角的核查员重新用不同措辞检索 2–3 次。默认"查不到就当作可疑"（`refuted=true`），而不是默认相信。核查结果连同修正建议写成独立文件，并在原证据文件中追加提示（不删除原文）。

## 7. 索引

最后通读全部文件，产出 `evidence/00_INDEX.md`：每文件摘要+来源数、核心数字速查表（附来源文件与置信度）、可用数据集清单（含字段与样本量）、方法学范本/理论框架文献各 8–12 篇、已知矛盾与待确认事项、对论文主题的初步可行性评估（3–5 条候选方向）。这份索引是 Phase 2 提案人唯一必读的长文件，其余证据文件按需查阅。
