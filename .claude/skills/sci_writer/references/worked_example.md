# 一次真实实践的浓缩记录

案例：安徽荃银高科种业股份有限公司（Winall Hi-tech Seed，中国杂交水稻种业企业），目标是中科院分区农林科学 2 区期刊。这份记录不是让你复用其内容（下一个案例的证据维度、数据源、统计模型都会完全不同），而是帮你校准"每一步该做多细、多严格"。

## Phase 1 实际发生的事

- 环境探测发现：容器内几乎所有中文站点（公司公告、行业数据库）与出版社站点都被代理拦截，只有 `github.com`/`raw.githubusercontent.com` 可达；WebSearch 可用但有会话配额；Consensus 月配额很快耗尽、Elicit 账号无 API 权限、Undermind/Scholar Gateway/PubMed 可持续使用。这个发现直接决定了后续所有代理的取数策略：中文一手数字靠 WebSearch 摘要，结构化数据靠搜索"GitHub 上有没有人爬过这类政府公告"。
- 意外发现：某个 GitHub 公开仓库把近 8000 条国家水稻品种审定公告文本汇编成了问答对数据集。这不是官方数据库，但用 Python 正则从中解析出了一个 2,386 条记录、核心字段覆盖率 92–99% 的品种级数据集——这是整个项目最终能有定量核心的关键。
- 数据可行性探针发现一个致命但可修复的缺口：数据源里"申请人"字段在四个特定年份（因数据源格式变化）完全缺失。解决办法是找到案例公司的品种命名规律（不育系/恢复系的专有代号），在有标签的子集上验证这个替代识别规则（精确率 1.000、召回率 0.770）后用于补全，同时保留这个验证过程作为独立证据文件。
- 十个证据维度全部完成后，用了约 10 次并行 Workflow/Agent 调用（分批次，因为后台 Workflow 任务在会话切换模型时被杀掉过一次，改用前台 Agent 补跑）。

## Phase 2 实际发生的事

- 主协调者自己先跑了探索性回归，发现了几个稳健信号（比如"表观产量上升趋势里,相对于当期对照的增产率完全没有趋势"），写进简报供提案人参考。
- 提前用学术检索工具查到一篇已经以同一案例公司为对象研究过"订单农业合同设计"的论文——这个警示避免了后续提案人重复设计一个已被占位的角度。
- 4 个提案人分别从"本学科技术角度""产业组织角度""政策评估角度""机制整合角度"独立提案，每个都实际跑了统计代码验证。
- 3 个评审（编辑视角、统计视角、新颖性视角）独立打分。**统计视角的复核彻底改变了结果**：它发现某个提案声称的核心估计量（等价于"用滚动对照连锁反解遗传增益"）的方差被低估了约 6 倍、关键的一步计算被后续同年数据证伪；也发现另一个提案用来证明"结论能推广到其他企业"的样本实际上 68% 都来自同一家公司，剔除这家公司后核心结果直接变号或归零。新颖性视角独立检索确认了两篇提案人自己没有引用、但内容几乎完全重叠的已发表方法学论文。
- 主协调者读完三份评审后，自己又做了一次独立复算去验证评审之间的分歧点（分通道重新估计效应，发现两类通道在时间上根本不重叠，不能合并处理），据此把最终主命题的表述从"两个并列的强结果"降级为"一个稳健结果 + 一个提示性结果"。

## 关键教训

1. **统计评审的独立复核是全流程性价比最高的一步**。三个提案里有两个的"稳健性"结论在独立复核后站不住脚，如果没有这一步,这些问题会一直带到 Phase 4 才被读者/审稿人发现。
2. **"已有人做过"的检索必须在提案阶段做，不能只在评审阶段做**。提案人自己动手核实过的创新点,到评审阶段更不容易被推翻。
3. **一个正则表达式的窗口宽度**（品质等级解析时,标准名与等级数字之间允许的字符间隔）**从 12 个字符放宽到 40 个字符，让覆盖率从 53.7% 提升到 65.8%**，进而改变了后续多个统计结论的显著性。数据解析阶段的小疏漏,后果会在几层之后才显现——这是主协调者应该亲自抽查解析结果、而不是全部信任下游代理的原因。
4. **多个并行 Workflow 可能重复劳动**：曾经出现两个批次的 Workflow 都在处理同一个证据维度的情况，靠定期检查 journal 进度及时发现并停掉了冗余任务。
