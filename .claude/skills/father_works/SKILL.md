# father_works：3414 肥料效应试验 → 投稿论文

这是一条从原始试验资料到可投稿 docx 的完整流水线，从一次真实的桐城市范岗镇水稻
"3414"试验论文整理任务中提炼而来。核心教训：**每一步都要用代码核实，不要凭经验
下笔**——产量换算、方程拟合、典型性检验、参考文献真实性、正文数字，全部可编程验证
的东西就不要靠"看起来对"。这条流水线走完一遍，实测能把审稿意见从几十条降到个位数。

## 这是一个长任务

预期涉及大量检索、多次往返修订，**默认使用 Workflow 工具做文献检索核验和多视角评审**
这两步（用户在最初的请求里说"可以使用子代理"或类似表述，就已经是明确的子代理编排
授权，不必每次重新征得同意；若当前会话开启了 Ultracode，本技能的检索核验与评审
两步天然符合其"编排 + 对抗式验证"的默认做法）。正文撰写、数据分析脚本、docx 生成
本身不需要子代理，串行做即可。

## 流程总览

```
1. 解压/解析原始资料  →  2. 统计再分析(analyze_3414.py)  →  3. 文献检索核验(Workflow)
        ↓                                                              ↓
6. 提交推送  ←  5. 多视角评审(Workflow) + 修订  ←  4. 撰写正文 + 生成 docx(build_docx.js)
```

先跑一次 `bash scripts/setup_env.sh` 把依赖装好（unrar、pandoc、LibreOffice、中文
字体、numpy/scipy/matplotlib、python-docx、docx npm 包）。

## 第 1 步：解析原始资料

用户给的通常是 rar/zip 压缩包，内含一份主试验记录（docx）和若干篇同类已发表论文
的 PDF（供参照体例、有时也提供数据佐证）。

```bash
unrar x -o+ 资料.rar 解压目录/     # 或 bsdtar -xf
python3 -c "
import docx
d = docx.Document('主记录.docx')
for p in d.paragraphs: print(p.text)
for t in d.tables:
    for r in t.rows: print(' | '.join(c.text.strip() for c in r.cells))
"
for f in *.pdf; do pdftotext -layout "$f" "${f%.pdf}.txt"; done
```

**逐字读完全部段落和表格**，不要只看摘要。原始资料常有内部矛盾或空缺——务必对照
检查：

- 正文叙述的施肥量与表格是否一致（常见错误：正文写一个数、表格按"3414"设计关系
  换算出另一个数）。3414 的水平关系是 1 水平=0.5×2 水平、3 水平=1.5×2 水平，用
  这个关系反推哪个数字是错的。
- 土壤养分、用药情况等字段是否为空白占位（原文常写"分别为　　"就断掉）。空的
  不要编，跑一遍 WebSearch 看能不能找到本地区同类型田块的区域参考值作背景对照，
  但绝不能冒充为本试验田的实测值——那是审稿人一眼识破的造假。留空并用醒目标记
  等作者填，在交付说明里写清楚"网络检索无法获得，需要化验单"。
- 若原文给出的"肥料效应方程"与"最高产量/最佳经济产量"数值互相矛盾（比如最佳经济
  产量反而高于最高产量），说明原文的方程拟合有误，本技能第 2 步会重新拟合，届时
  以重新计算的结果为准，并在交付说明里指出原文的问题。

## 第 2 步：统计再分析

**不要手算任何数字。** 把小区产量、施肥水平、经济性状整理成 `trial.json`
（格式见 `scripts/analyze_3414.py` 顶部的文档字符串），跑：

```bash
python3 scripts/analyze_3414.py trial.json data.json
```

它会输出：14 个处理的产量/经济性状/效益全表、三元二次方程及典型性检验（驻点、
Hessian 特征值、是否落在试验范围内）、三个单因素的一元二次/线性/线性加平台方程
及显著性、缺素区相对产量与土壤供肥能力评价、相邻水平间的边际效益、性状与产量的
相关分析。

跑完看它打印在终端的判断摘要——三元二次方程是否通过典型性检验、各单因素是否
显著、拐点在哪——**这些判断直接决定正文怎么写**，不要自己再判断一遍。方法学细节
（为什么要看 Hessian 特征值、典型性检验的两个条件、单因素方程残差自由度为什么
只有 1、线性加平台的适用场景、相对产量分级的临界敏感性、经济效益里"纯收益"这个
词为什么用不得）见 `references/analysis-methods.md`——**写讨论和结论之前务必读**，
里面写的是这些数字能支撑到什么表述程度，不是纯算法文档。

需要图时用 matplotlib（600 dpi，Unicode 上下标而非 LaTeX 语法，字体走
`WenQuanYi Zen Hei` 保证中文能显示），单因素效应三合一图是标配。

## 第 3 步：真实参考文献检索核验

目标 20~26 条真实、可核实、格式规范的中文文献。**这一步几乎肯定要用 Workflow**：
多个检索员并行按类别（方法学、本省同类试验、省外同类试验、作物营养、土壤丰缺
指标、化肥减量、品种背景等）search，每条候选再经独立的"怀疑论核验员"复核，通过
阈值的才收录。

务必先读 `references/reference-verification.md`——里面讲了这一步最容易踩的坑：
知网/万方/维普/百度学术在这类会话环境通常被网络策略拦截，只能靠 WebSearch 换着
检索式试；作者人数经常被搜索摘要截断到 3 位，必须每条核实真实作者数再决定要不
要加"等"；查不到关键字段（尤其年份）的条目该删就删，不要编。

核验通过后，把结构化字段（作者、题名、刊名、年、卷、期、页）填进
`refs_data.json`（结构见 `assets/refs-example.json`），跑：

```bash
node scripts/make_refs.js refs_data.json > refs.js
```

自动生成 GB/T 7714—2015 顺序编码制著录字符串，作者超 3 位自动加"等"（前提是你
填的是完整作者名单，不要自己先截断）。

## 第 4 步：撰写正文并生成 docx

正文写进 `content.js`（结构参照 `assets/content-example.js`，那是一篇完整定稿的
真实样例，标记约定见文件顶部注释：`^{}` 上标、`_{}` 下标、`*{}` 斜体、
`[[key]]` 文献引用、`【】` 需作者补充的占位）。期刊体例（字体字号、标题层级、
三线表、量符号斜体、参考文献格式）的完整规范见 `references/journal-format.md`，
**动笔前先读**，比写完再改省事得多。

`scripts/build_docx.js` 已经实现了：中英文摘要与关键词、章节自动编号、三线表
（含合并单元格）、图片插入、GB/T 7714 引用序号自动分配与连续区间合并
（`[5,7-8]`）、数学减号替换、首页脚注（基金/简介/收稿日期）、页码。改内容不用碰
这个脚本，改 `content.js` 就够：

```bash
node scripts/build_docx.js refs.js manuscript.docx
```

**生成后必须转 PDF 逐页看**，不要只看 Word 大纲或信任脚本没报错：

```bash
soffice -env:UserInstallation=file:///tmp/lo_profile --headless --norestore \
  --convert-to pdf --outdir . manuscript.docx
pdftoppm -jpeg -r 75 manuscript.pdf page   # 生成 page-01.jpg ... 逐页 Read 查看
```

重点看表格是否跨页断裂、公式是否把版面拉得字距异常、标题层级是否视觉递减、参考
文献两端对齐是否把中文责任者拉出大空隙。

然后跑数字核查：

```bash
pandoc manuscript.docx -t markdown --wrap=none -o manuscript.md
python3 scripts/check_numbers.py data.json manuscript.md
```

它会把正文里所有数字与 data.json 做容差匹配，列出对不上的（多数是原始资料/文献
里的数字，正常；少数才是真错误，逐条看上下文分辨），并检查未设重复情形下是否误用
了"显著"等统计学推断措辞。

## 第 5 步：多视角评审与修订

正文和数据都通过自检后，用 Workflow 跑一次六视角评审：数据核查、统计、期刊格式、
文献引用、写作、模拟审稿人。每个视角独立读全部材料（manuscript.md、content.js、
data.json、refs.js、原始资料）产出意见，再对每条意见做一次对抗式核验（独立核实
是否属实、给出精炼修改），最后汇总成排序过的修订清单。

评审提示词直接用 `references/review-checklist.md` 的六个分类作为六个评审员的
角度，把这份清单发给每个评审员当作检查依据；也可以自己不跑 Workflow、独自对照
这份清单过一遍，覆盖率会低一些但能挡掉大部分问题。

拿到意见后**逐条核实再改**，不要照单全收（评审意见本身也可能站不住），也不要
筛选性接受（数据类、统计类的 major 意见基本都是真问题）。改完重新生成 docx、
重新转 PDF、重新跑 check_numbers.py，确认修订没有引入新的不一致。

如果用户后续要求删除某条无法核实的文献、替换某个数据，直接照办，改完立刻重新
生成 docx 发给用户，不要拖到下一轮评审再说——用户等的是能马上看的文件。

## 第 6 步：交付

- 把 docx、排版预览 PDF、图片、全部分析脚本与中间数据（data.json、trial.json、
  content.js、refs.js、refs_data.json）一起提交到用户指定的分支，写清楚脚本如何
  复现。
- README 或交付说明里列出还需作者补充的内容（黄色高亮项），以及本次处理中发现
  并订正的原始资料问题（矛盾的施肥量、方程与数据不符等）。
- 用 SendUserFile 把 docx 发给用户，caption 里说清楚这一版改了什么。
- 若仓库没有默认分支或另一分支属于无关项目，不要强行开 PR，向用户说明原因。
